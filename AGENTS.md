# Инструкции для работы с pet-care-v2

Эти правила действуют для всего репозитория. Перед изменением вложенного каталога
проверь наличие более конкретного `AGENTS.md`. Отвечай пользователю на русском языке.

## Назначение и структура

Pet Care — приложение для ухода за питомцами: профили, задачи, ветеринарные визиты
и записи, запасы, покупки и уведомления.

| Каталог | Назначение |
| --- | --- |
| `services/backend` | Java 25, Spring Boot 4, Spring Security/JWT, Spring Data JPA, Flyway, Maven Wrapper |
| `apps/web` | React, TypeScript, Vite, React Router, CSS, Oxlint |
| `apps/mobile` | React Native, Expo, TypeScript; запуск на Android, iOS и web |
| `infra` | Docker Compose с PostgreSQL 17 |
| `docs` | Описание интеграций и дизайн-спецификации |
| `uploads` | Файлы времени выполнения; не добавляются в Git |

Корневого `package.json` и общей команды сборки нет. Запускай команды из каталога
соответствующего приложения. Актуальные версии и скрипты проверяй в его манифесте.
Инструкции запуска находятся в `README.md` и `SETUP-VSCODE.md`.

## Порядок работы

- Сначала выполни `git status --short`, изучи связанные файлы, тесты и документацию.
  Сохраняй существующие незакоммиченные и неотслеживаемые файлы пользователя.
- Для сложной задачи составь краткий план. Если неизвестное бизнес-правило существенно
  влияет на решение, уточни его до реализации зависящей от него части.
- Делай минимальные изменения в рамках задачи, используй существующие компоненты
  и утилиты. Не добавляй зависимости и не меняй архитектуру без необходимости.
- Следуй стилю конкретного файла: web и mobile используют разное форматирование.
- Не создавай коммиты и не выполняй push без явного запроса. Не выполняй reset,
  rebase, force push и удаление пользовательских данных без согласования.
- После изменений выполни соответствующие проверки и просмотри итоговый diff.
  Обновляй документацию при изменении интерфейсов, настройки или поведения.

## Backend и API

- Java-код находится в `services/backend/src/main/java/com/petcare/backend`.
  Сохраняй группировку по предметным областям (`pet`, `task`, `vet`, `food`,
  `shopping`, `notification`, `device`, `user`).
- Следуй существующему разделению: контроллеры принимают HTTP-запросы и DTO,
  сервисы реализуют бизнес-логику и транзакции, репозитории работают с БД.
  Используй конструкторное внедрение зависимостей.
- Базовый путь API — `/api/v1`. Проверяй входные DTO средствами Jakarta Validation
  и обрабатывай ошибки через `error/GlobalExceptionHandler`.
- Проверяй владельца каждого пользовательского ресурса на сервере. Сохраняй
  существующее поведение `404` для чужих и несуществующих ресурсов.
  Не доверяй идентификатору владельца из клиентского запроса.
- Сохраняй контракты PATCH: `null` обычно означает «без изменений»;
  очистку поля реализуй по правилам конкретного endpoint. Не унифицируй эти правила
  без изучения DTO, сервиса и тестов.
- Сохраняй идемпотентность завершения задач и покупки. Покупка с пополнением запасов
  должна оставаться атомарной. Проверяй побочные эффекты повторяющихся задач
  и списания корма при изменении соответствующих сервисов.
- Моменты времени передавай и сохраняй в UTC, отображай в локальном часовом поясе.
  Календарные даты, например дату рождения или визита, не превращай в UTC-моменты.
- При изменении контракта API проверь оба клиента: `apps/web/src/api` и
  `apps/mobile/src/api`. Типы и клиенты хранятся отдельно, общей генерации нет.

## База данных и миграции

- Изменяй схему через новые Flyway-миграции в
  `services/backend/src/main/resources/db/migration`.
  Перед выбором версии проверь все миграции, включая неотслеживаемые файлы.
- Не редактируй уже применённые миграции: это меняет контрольные суммы.
  Не отключай Flyway и не заменяй `ddl-auto=validate` автоматическим изменением схемы.
- Рабочая локальная БД — PostgreSQL, тестовая — H2 в режиме PostgreSQL.
  Общие миграции загружаются из `db/migration`, варианты для конкретной БД —
  из `db/vendor/postgresql` и `db/vendor/h2`. Используй вариант по образцу V10,
  если SQL действительно требует различий между СУБД.
- Согласовывай JPA-маппинг с SQL-типами, ограничениями и индексами.
  Успешные H2-тесты не доказывают совместимость специфичного PostgreSQL SQL.
- Не удаляй Docker volumes, не очищай БД и пользовательские загрузки ради проверки.

## Web и mobile

- Используй существующие `src/api/client.ts`, `src/api/types.ts` и механизмы
  `src/auth`; не дублируй работу с JWT и обработку API-ошибок в экранах.
- Web: маршруты находятся в `src/App.tsx`, общий каркас —
  `src/components/layout/AppShell.tsx`. Переиспользуй компоненты модалок,
  подтверждения и дизайн-токены из `src/styles/tokens.css`.
- Web обращается к `/api/v1`; Vite проксирует `/api` и `/files` на backend.
  Не подставляй адрес конкретного компьютера в компоненты.
- Mobile: используется собственная навигация в `src/navigation/AppStack.tsx`.
  Расширяй её по существующему образцу; не заменяй библиотекой без необходимости.
- Mobile: переиспользуй `src/theme`, `components/Typography.tsx`, `ScreenHeader`
  и `DateField`. Учитывай реализации `DateField.tsx` и `DateField.web.tsx`.
- Адрес backend для mobile задаётся через `EXPO_PUBLIC_API_URL`.
  На физическом устройстве `localhost` относится к самому устройству.
- Учитывай состояния загрузки, пустых данных, ошибок и повторной отправки форм.
  Для изменений UI проверяй затронутые пользовательские сценарии; для mobile
  указывай, на каких платформах выполнена проверка.

## Безопасность и внешние сервисы

- Не выводи и не добавляй в Git содержимое `.env`, JWT, пароли, ключи и токены.
  Публичные переменные `EXPO_PUBLIC_*` не подходят для секретов.
- Сохраняй ограничения размера и типов загрузок, проверку владельца и защиту
  от выхода за пределы каталога файлов в `file/FileStorageService`.
- Не отключай аутентификацию, авторизацию или валидацию ради прохождения проверок.
- Тесты должны оставаться изолированными от реальной отправки push и email.
  Для изменений календарной интеграции изучи `docs/google-calendar.md`
  и фактическую реализацию перед расширением поведения.

## Команды проверки

Выполняй команды из указанного рабочего каталога. Устанавливай зависимости только
при необходимости; для установки по существующему lock-файлу используй `npm ci`.

| Изменения | Рабочий каталог | Проверки |
| --- | --- | --- |
| Backend, API, миграции | `services/backend` | `./mvnw clean test` (нужен JDK 25) |
| Web | `apps/web` | `npm run lint` и `npm run build` (включает `tsc -b`) |
| Mobile | `apps/mobile` | `npx --no-install tsc --noEmit` и проверка затронутого сценария в Expo |
| Только документация | Корень репозитория | Проверка путей, команд, содержания и `git diff --check` |

- Backend-тесты находятся в `services/backend/src/test/java/com/petcare/backend`.
  Переиспользуй подход существующих `*FlowTest`: Spring Boot, MockMvc, H2 и Flyway.
- Для нового поведения добавляй тесты; для исправлений проверяй регрессию,
  граничные случаи и изоляцию владельцев, когда это относится к задаче.
- У web и mobile сейчас нет настроенных скриптов автоматических тестов.
  Проверка типов и сборка не заменяют проверку поведения. Не внедряй новый
  тестовый стек без необходимости для задачи.
- Не утверждай, что проверка прошла, если она не запускалась. Укажи команду,
  результат и причину, если запуск заблокирован окружением или зависимостями.
