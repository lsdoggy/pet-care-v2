# Отправка ветеринарных визитов из 1С в Pet Care

## Подключение и сопоставление

Оператор Pet Care предоставляет HTTPS-адрес и отдельный Bearer-токен для интеграции. На одном экземпляре приложения токен связан с одним настроенным питомцем и одним названием клиники. Оператор задаёт `PETCARE_VETINFO_TOKEN`, `PETCARE_VETINFO_PET_ID` и `PETCARE_VETINFO_CLINIC_NAME`. Имя клиники после обрезки пробелов должно содержать от 1 до 150 символов. Сервер определяет владельца по выбранному питомцу.

Перед включением выгрузки оператор и клиника подтверждают соответствие локальной карточки пациента конкретному питомцу Pet Care. В 1С храните подтверждённое соответствие вместе с настройкой подключения. При совпадении имён, отсутствии соответствия или смене владельца приостановите отправку и передайте случай ответственному сотруднику для проверки с оператором Pet Care. Имя, телефон и другие данные владельца для сопоставления через API не нужны.

## Запрос и ответ

`POST https://<хост Pet Care>/api/v1/vetinfo` с заголовками `Authorization: Bearer <токен клиники>` и `Content-Type: application/json`. Тело — JSON в UTF-8.

| Поле | Тип | Правила |
| --- | --- | --- |
| `scheduledAt` | строка | Обязательно. Дата и время визита в ISO 8601 со смещением или `Z`. |
| `durationMinutes` | целое число | От 5 до 480. По умолчанию 30. |
| `doctorName` | строка | До 150 символов. |
| `address` | строка | До 255 символов. |
| `cost` | число | От 0 до 99999999.99. Передавайте до двух знаков после точки, как в денежном поле Pet Care. |
| `currency` | строка | Ровно три латинские буквы. Сервер переводит их в верхний регистр, справочник валют не проверяет. |
| `notes` | строка | До 2000 символов. |
| `reason` | строка | До 2000 символов. |

Все поля, кроме `scheduledAt`, можно опустить. Минимальный корректный запрос и пример с необязательными полями:

```json
{"scheduledAt":"2026-12-10T08:30:00Z"}
```

```json
{
  "scheduledAt": "2026-12-10T11:30:00+03:00",
  "durationMinutes": 30,
  "reason": "Плановый осмотр",
  "cost": 1500.00,
  "currency": "RUB"
}
```

Ответ `201 Created` содержит `{"appointmentId":123}`. В истории питомца появляется визит со статусом `SCHEDULED`, даже если выгрузка запущена при закрытии приёма в 1С. Идентификатор можно сохранить в локальном журнале рядом с номером документа 1С.

Примеры с ответом `400 Bad Request` при действующем токене и настроенном подключении:

```json
{}
```

```json
{"scheduledAt":"2026-12-10T08:30:00Z","durationMinutes":4,"currency":"RUB1"}
```

## Отправка из 1С

При закрытии приёма создайте запись в очереди отправки с локальным идентификатором документа и подготовленными полями визита. Выгружайте фоновой задачей после сохранения документа. Один документ в рамках подключения должен иметь одну запись в очереди. Последовательная обработка или блокировка записи помогает избежать двух одновременных отправок из 1С.

Ниже иллюстративный псевдокод на встроенном языке 1С. Доступ к очереди, преобразование даты с учётом часового пояса, чтение секрета, разбор JSON и запись результатов зависят от конфигурации.

## Ошибки и повторная отправка

| Результат | Действие |
| --- | --- |
| `400` | Исправить JSON или поля. Для ошибок валидации полей API возвращает сведения в `details`. |
| `401`, `403` | Проверить токен и доступ с оператором. Пользовательский JWT не даёт права отправлять визиты через этот маршрут. |
| `404` | При верном URL оператору нужно проверить, что настроенный питомец существует и активен. |
| `415` | Проверить `Content-Type: application/json`. |
| `503` | Проверить с оператором конфигурацию питомца и имени клиники. Если ответ пришёл от прокси, сначала сверить результат отправки. |
| Таймаут, обрыв связи, прочие `5xx`, потеря тела ответа `201` | Остановить автоматический повтор. Визит мог сохраниться до потери ответа. |

Каждый принятый POST создаёт визит. Маршрут не поддерживает `Idempotency-Key`, поиск по номеру документа или чтение истории с токеном клиники. При неопределённом результате попросите владельца проверить историю настроенного питомца и сверить время и данные визита. Если результат остаётся неоднозначным, оставьте документ на ручной сверке. Повторяйте отправку только после подтверждения, что визит не был создан. Для подтверждённого сбоя до отправки запроса можно применить ограниченный backoff, например 30 секунд, 2 минуты и 5 минут.

## Доступ и проверка

- Используйте HTTPS с проверкой сертификата сервера. Храните токен в защищённом хранилище с доступом только для учётной записи интеграции и уполномоченных администраторов. При отзыве доступа оператор меняет или удаляет токен и перезапускает backend.
- Передавайте только данные, необходимые для визита. Уточните правовое основание передачи и необходимость согласия у ответственного за обработку данных. Не включайте данные владельца в `notes` и `reason`. В журнале интеграции достаточно локального ID, времени, кода ответа и полученного `appointmentId`, без токена и полного тела.
- Согласуйте тестовое окружение с оператором. Настройте подключение на отдельного тестового питомца и используйте вымышленные данные. Отправьте минимальный запрос, сохраните ID и проверьте визит в истории под учётной записью владельца. Другой пользователь не должен видеть визит.
- Проверьте `401` без токена, `403` с пользовательским JWT и `400` без `scheduledAt`. Имитируйте потерю ответа в тестовой очереди 1С и проверьте переход к ручной сверке.

## Ограничения и возможные доработки

Текущий маршрут передаёт данные визита. Диагноз, назначения и вложения через него не принимаются. Для подключения нескольких клиник и питомцев потребуются отдельные учётные данные клиник и явные подтверждённые соответствия пациентов. Внешний идентификатор документа с уникальностью в пределах клиники или ключ идемпотентности позволил бы безопасно повторять отправку. Отдельный способ получить результат по этому идентификатору упростил бы сверку после таймаута.
