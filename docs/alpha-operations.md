# Эксплуатация закрытой альфы

## Развёртывание и мониторинг

Укажите публичный домен в `API_DOMAIN`, направьте DNS на VPS и заполните
`infra/.env` по образцу `.env.example`. Используйте тот же HTTPS-домен для
ссылок восстановления и адреса API в подписанной Android-сборке.

Выполните из `infra`:

```bash
docker compose --env-file .env -f compose.vps.yml config --quiet
docker compose --env-file .env -f compose.vps.yml up -d --build --wait
docker compose --env-file .env -f compose.vps.yml ps
curl --fail --silent --show-error https://petcare.example/api/v1/health
curl --fail --silent --show-error --output /dev/null https://petcare.example/
```

Проверьте миграции Flyway в журнале backend после запуска. Настройте проверку
`/api/v1/health` из внешней сети каждые 5 минут и оповещение ответственного
при трёх последовательных сбоях. Добавьте оповещения о заполнении диска
на 80% и о копии старше согласованного интервала. Для диагностики доставки
проверяйте события у SMTP-провайдера и результаты в контрольных аккаунтах
на Android и iPhone. Фиксируйте время, канал и итог без email, токенов и ссылок
в отчёте. Успешный ответ HTTP health подтверждает доступность сервера.

Если нужно остановить набор, установите `APP_REGISTRATION_ENABLED=false` и
выполните `docker compose --env-file .env -f compose.vps.yml up -d --no-deps backend`.
Проверьте отказ регистрации с неиспользованным приглашением и вход действующего
тестового пользователя. Зафиксируйте причину остановки в канале поддержки.

## Резервная копия базы и загрузок

Команды выполняются из `infra` на VPS. Согласуйте окно обслуживания.
На время копирования backend недоступен. Если к той же БД или тому загрузок
подключены процессы вне Compose, остановите запись и с их стороны.

```bash
docker compose --env-file .env -f compose.vps.yml stop backend
bash backup-alpha.sh "$HOME/petcare-backups"
docker compose --env-file .env -f compose.vps.yml start backend
```

Выполните последнюю команду и при ошибке копирования. После старта проверьте
`/api/v1/health` через внешний HTTPS. Скрипт выводит путь к каталогу с
`database.dump`, `uploads.tar.gz` и `SHA256SUMS` после записи всех файлов.
Перенесите каталог в закрытое хранилище вне VPS. Установите срок хранения и включите
в мониторинг возраст последней полной копии и свободное место на диске.

## Пробное восстановление

Используйте фиктивные аккаунты, фото и PDF. Выполняйте команды из `infra`.
Выберите новое имя Compose-проекта для каждого прогона. Это создаст отдельные тома
БД и загрузок. Используйте ту же ревизию кода и образ backend, что при копировании.

```bash
snapshot=/absolute/path/to/alpha-backup
(cd "$snapshot" && sha256sum -c SHA256SUMS)

restore=(
  env MAIL_HOST= MAIL_USERNAME= MAIL_PASSWORD= MAIL_FROM=
  EXPO_PUSH_ENABLED=false EXPO_PUSH_ACCESS_TOKEN=
  WEB_PUSH_VAPID_PUBLIC_KEY= WEB_PUSH_VAPID_PRIVATE_KEY= WEB_PUSH_VAPID_SUBJECT=
  APP_ACCOUNT_RECOVERY_PAGE= APP_PASSWORD_RESET_PAGE=
  docker compose --env-file .env -f compose.vps.yml -p petcare-restore-drill-01
)
"${restore[@]}" up -d --wait postgres

"${restore[@]}" exec -T postgres sh -ec '
    export PGPASSWORD="$POSTGRES_PASSWORD"
    exec pg_restore --exit-on-error --host=127.0.0.1 --username="$POSTGRES_USER" --dbname="$POSTGRES_DB"
' < "$snapshot/database.dump"

"${restore[@]}" run --rm --no-deps -T --entrypoint tar backend \
    -C /app/uploads --no-same-owner -xzf - < "$snapshot/uploads.tar.gz"

"${restore[@]}" up -d --wait backend
"${restore[@]}" exec -T backend curl --fail --silent http://127.0.0.1:8080/api/v1/health
```

Продолжайте только после успешного завершения каждой команды. Caddy в проекте
восстановления не запускайте. Перед восстановлением копии с реальными данными
дополнительно запретите исходящий трафик стенда к внешним SMTP и push-сервисам.
На изолированном стенде проверьте вход тестовых
пользователей, существующие записи, открытие PDF и фото владельцем и изоляцию
между аккаунтами. Запишите ревизию кода, версии образов, дату копии, длительность
восстановления и результаты проверок.

## Допуск участников

- Зафиксируйте ревизии backend и web, версию и номер подписанной Android-сборки.
- Проверьте внешний HTTPS и миграции. Настройте оповещения о сбоях API, SMTP
  и push, заполнении диска и пропусках резервного копирования.
- Подтвердите изоляцию аккаунтов, восстановление резервной копии, оба сценария
  email и доставку уведомлений на физических Android и iPhone по чек-листам
  [#34](https://github.com/lsdoggy/pet-care-v2/issues/34) и
  [#53](https://github.com/lsdoggy/pet-care-v2/issues/53).
- Назначьте канал поддержки и ответственного за запросы об удалении данных.
  Согласуйте сроки удаления и порядок обращения с резервными копиями.
  Проверьте, что отключение регистрации останавливает приём новых участников.
- Начните с внутреннего прогона на фиктивных данных. После допуска пригласите
  10–15 участников. Расширяйте группу до 100 после устранения блокирующих проблем.

## Памятка участнику

- Получите приватное одноразовое приглашение и адрес приложения у оператора.
- На Android установите APK из канала поддержки. На iPhone добавьте веб-приложение
  на экран «Домой» из Safari. Инструкции доступны отдельно.
  [Android](alpha-android-push.md), [iPhone](alpha-web-push.md)
- Проверьте вход и включите уведомления на своём устройстве. Для восстановления
  доступа используйте форму на экране входа. [Восстановление доступа](alpha-email.md)
- Сообщайте о сбоях через канал поддержки. Приложите версию сборки, модель
  устройства, шаги и время сбоя. Для запроса удаления данных свяжитесь
  с оператором через тот же канал.

## Локальный прогон восстановления

На PostgreSQL 17.12 прошёл прогон с двумя временными Compose-проектами и
существующим локальным образом backend для работы с томом. Контрольные суммы
дампа и архива совпали. После восстановления подтвердились значение строки
в тестовой таблице и байты файла в томе. Для релизной приёмки повторите процедуру
с актуальным образом, схемой Pet Care и проверкой чтения через клиенты.

В расширенном локальном прогоне PostgreSQL 17.12 применил миграции до V22.
Caddy отдал страницу восстановления и health API по HTTPS с локальным CA.
Два аккаунта созданы через приглашения. Через API один из них загрузил
тестовый PDF. До и после восстановления оба URL вложения вернули те же
байты владельцу, 401 без сессии и 404 другому аккаунту. Восстановленная
запись читалась через API с исходным содержимым. Этот прогон использовал
локальный JAR и временные контейнеры, а также сгенерированные тестовые данные.
