# Design

## Context

Мотивация описана в proposal.md. Изменение пересекает два независимых React-клиента, поэтому нужен общий поведенческий контракт при разных механизмах жизненного цикла.

- Web `apps/web/src/lib/dashboard.ts` сравнивает dueAt с Date.now(); HomePage мемоизирует группы только по данным. Mobile `apps/mobile/src/lib/dashboard.ts` использует начало дня и endToday через +86400000, а DashboardScreen также мемоизирует результат по данным.
- Web QuickAddPurchaseModal вызывает createFoodProduct; mobile inline QuickPurchaseModal вызывает createShoppingItem, но пропускает дробное количество и значения выше 999.
- Оба API-клиента уже имеют createShoppingItem. Backend принимает customName, Integer quantity (1–999) и StockUnit, defaults 1/PCS. Дедупликация существует для linked productId, но не для customName.
- В package.json обоих клиентов нет test script. Backend FoodShoppingFlowTest проверяет custom-покупки и linked-пополнение, но не клиентский сценарий быстрой покупки.

## Goals / Non-Goals

**Goals:**
- Детерминированные вычисления с явно переданным now и одинаковыми граничными примерами на обеих платформах.
- Единый результат быстрой покупки без расширения API и независимый от успешности последующего refresh dashboard.
- Минимальная тестовая поддержка чистой логики и взаимодействия формы с API.

**Non-Goals:**
- Создание нового shared-package и перестройка сборок независимых приложений ради нескольких helpers.
- Паритет ленты событий, лимитов внимания, визитов, навигации и прочих форм Shopping/Stock.
- Серверная идемпотентность, дедупликация customName, исправление часов устройств или смена источника времени на серверный.

## Decisions

### 1. Чистая классификация с одним снимком времени

В каждом клиенте сохранить локальный чистый helper с явным now. Сначала исключить DONE, затем сравнивать epoch-моменты dueAt/now, затем календарные компоненты локальной даты. Не использовать прибавление фиксированных 24 часов для определения локального дня. Для одного пересчёта групп, сортировки, счётчиков и индикаторов использовать один снимок now. Подпись «Сегодня, 10:00» допустима у просроченной задачи лишь вместе с явным признаком просрочки; подпись не должна противоречить группе.

Альтернатива «просрочено после полуночи» отвергнута пользователем: игнорирует заданное время. Серверная классификация не нужна: текущий контракт возвращает dueAt, а результат сравнения моментов уже независим от часового пояса; локальный пояс влияет только на «Сегодня».

### 2. Лёгкие часы dashboard и жизненный цикл

На смонтированном активном dashboard обновлять now периодически с интервалом не более 60 секунд и немедленно при восстановлении активности: web visibility/focus, mobile AppState active. Пересчитывать зависимые view-model без сетевого запроса на каждый тик. Таймеры и слушатели очищать при unmount; фоновые таймеры не считать гарантией актуальности. Включить now в зависимости memo; передавать его и в существующий builder ленты, сохраняя разные правила включения событий.

Порог 60 секунд — технический допуск отображения, а не льготный период: при любом пересчёте строго действует dueAt < now. Альтернатива таймеру на каждый срок сложнее в очистке и не даёт пользы для минутного UI.

### 3. Custom-покупка на существующем endpoint

В web заменить payload и callback FoodProductDto на ShoppingListItemDto либо callback успеха без DTO, если объект не нужен вызывающему коду. Убрать категорию/выбор единицы и текст про запасы/подсказки; добавить количество. Mobile привести к тем же ограничениям. Отправлять только `{customName: name.trim(), quantity, unit: 'PCS'}`, без productId и запросов создания продукта.

Валидацию держать в чистых локальных helpers, проверять длину после trim, непустое количество, конечное число, целочисленность и диапазон. Поддержать точку/запятую при разборе числового ввода без округления дробей. Предотвращение ввода сверх лимита допустимо вместо отдельной ошибки, если пользователь может исправить значение.

Альтернатива переносу web-поведения на mobile отвергнута: создаёт запись каталога, а не покупку. Серверные defaults остаются совместимыми, но клиент посылает значения явно ради одинакового запроса.

### 4. Отдельные исходы POST и refresh

Заблокировать повторный submit синхронным in-flight guard и disabled-состоянием до завершения POST. При ошибке POST сохранить поля, показать ошибку и разрешить повтор. При успехе закрыть/сбросить форму; существующее обновление dashboard выполнять отдельно, не превращая его ошибку в ошибку создания и не повторяя POST. До отправки отмена ничего не меняет; после отправки закрытие не означает отмену серверной операции.

Это защита от double tap в одной форме, не exactly-once доставка: при потере ответа сервер мог создать custom-позицию. Новый idempotency key и серверную дедупликацию не добавлять.

### 5. Проверка паритета, а не только сборка

Добавить минимальные локальные unit/component-test настройки совместимые с версиями React/Vite и Expo, не менять production toolchain. Проверять один и тот же набор фиксированных моментов и полей в обоих клиентах. API мокировать; утверждать наличие POST shopping и отсутствие POST food-products. Таймеры и foreground проверять fake clock/lifecycle событиями, а native keyboard/lifecycle дополнительно проверить вручную.

### 6. Однозначные web auth-модули

Дополнительный согласованный scope: переименовать компонентный модуль AuthContext.tsx в AuthProvider.tsx и обновить импорт App.tsx. Оставить authContext.ts единственным модулем контекста, который используют провайдер и useAuth. Это устраняет неоднозначность TypeScript на Windows без изменения session/bootstrap/API/tokenStore. Regression-тест монтирует реальный AuthProvider с useAuth, проверяет загрузку сохранённой сессии и logout; штатная production-сборка проверяет реальные импорты, не только тестовые моки.

Ручные проверки web/mobile по задачам 4.2–4.3 остаются обязательными при доступе к браузеру и устройству; автоматические component-тесты не объявляются их заменой.

## Risks / Trade-offs

- [Разные/неверные часы устройств] → одинаковый алгоритм гарантирует результат при одинаковом now, но не синхронизирует устройства; это вне change.
- [Фоновые таймеры приостанавливаются] → немедленный пересчёт при foreground и очистка ресурсов.
- [DST и локальная полночь] → календарное сравнение дат и проверки нескольких TZ, без фиксированного endToday +24h.
- [Дубли после сетевого таймаута] → не обещать серверную идемпотентность; guard предотвращает только параллельные отправки из одной формы.
- [Старые клиенты продолжают прежнее поведение] → выпустить web и mobile согласованно; сервер остаётся совместимым.
- [Новый test runner несовместим с React/Expo] → использовать поддерживаемые версии и отдельно проверить unit/component suite и штатные сборку/typecheck.

## Migration Plan

1. Реализовать и проверить оба клиента по delta specs; backend/БД не менять.
2. Проверить реальные dashboard и переход в список покупок на web/mobile; затем выпустить оба клиента.
3. Ранее созданные web-продукты с нулевым остатком не удалять и не преобразовывать автоматически: они могут быть нужны пользователю.
4. Откат — возврат предыдущих клиентских сборок без миграций. Уже созданные custom-покупки остаются валидными для старых клиентов.
